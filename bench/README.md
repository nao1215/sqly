# Benchmarks

sqly is measured the way a user runs it, one process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds sqly, runs each command in interleaved rounds, and reports latency, CPU time, peak RSS and, for the large inputs, throughput.

```console
$ go install github.com/nao1215/himorime@latest
$ make bench            # himorime run bench
$ make bench-compare    # himorime compare --against main bench
$ make bench-docs       # sqly against trdsql, csvq and textql, written into website/content/about.md
```

## Regression suite: himorime.yaml

`make bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v1.7.0 make bench-compare` compares against another revision. `himorime run --filter 'import 100k' bench` measures one benchmark, and `himorime run --tag shell bench` the interactive shell.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

The inputs are generated by `gen.sh` before measuring, so no fixture is added, and both revisions run the working tree's `gen.sh`. `customers 100k` reads the committed `testdata/benchmark/customers100000.csv`.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `sqly --version` | starting sqly |
| `query 10` | `--output-format` csv, json, table | a query over 10 rows, where start-up and the import dominate |
| `query 100k` | `--output-format` csv, json, jsonl | importing 100 000 rows, turning every row of the result into values, and writing each format |
| `query 10k` | `--output-format` csv, table | the table format, which measures every column before printing |
| `import 100k` | `--sql 'SELECT COUNT(*) ...'` | importing 100 000 rows of mixed types |
| `import 1m` | `--sql 'SELECT COUNT(*) ...'` | importing 1 000 000 rows (5 runs) |
| `import 8 files` | a directory of 8 CSV files | loading several files into one session |
| `customers 100k` | a range, sorted, from the customers file | the historical benchmark of sqly |
| `query error` | a query on a missing table | the error path, with its hint, exit 1 |
| `shell start` | the shell, `.exit` | opening the interactive shell on a terminal |
| `shell completion 50 tables` | a query and Tab over 50 tables | completion of table and column names, asked on every key |
| `shell file completion` | `.import` and Tab in a 50 by 50 tree | completion of a path inside one leaf directory |
| `shell highlight 50 columns` | a SELECT of 50 columns | highlighting and redrawing the statement on every key |

The `shell` benchmarks run sqly on a pseudo-terminal (`terminal: true`, Linux and macOS) and type the input one key at a time, waiting until sqly has read each key, so the work sqly does per key is done for every key. Their latency includes that typing; CPU time is what shows the work per key.

Numbers from different machines are not comparable; compare revisions on one machine, as `make bench-compare` and CI do.

## Comparison suite: compare/himorime.yaml

`compare/himorime.yaml` runs the same query with sqly, [trdsql](https://github.com/noborus/trdsql), [csvq](https://github.com/mithrandie/csvq) and [textql](https://github.com/dinedal/textql) on the customers file: the top 10 countries by row count, printed as CSV. Before measuring, a setup step checks that the four outputs are the same bytes.

It is not a CI gate: CI only validates it. `make bench-docs` needs the three tools on PATH, runs the suite, and replaces what is between the `himorime:begin benchmarks` and `himorime:end benchmarks` markers in `website/content/about.md`, with the machine and the tool versions under the tables. The versions measured are:

```console
$ go install github.com/noborus/trdsql/cmd/trdsql@v1.2.3
$ go install github.com/mithrandie/csvq@v1.18.1
$ go install github.com/dinedal/textql/textql@2.0.3
```

trdsql and textql need cgo (SQLite); sqly and csvq do not.
